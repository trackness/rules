# Contributing

## Workflow

- Branch from `main`, naming the branch `<type>/<description>` per [Conventional Branch](https://conventionalbranch.org/): `feature/` (or `feat/`), `bugfix/` (or `fix/`), `hotfix/`, `release/` or `chore/`, lowercase and hyphen-separated.
- Write commit messages and the pull request title per [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/), such as `feat: add …` or `fix: …`.
- To try a change in a Claude Code session, start it from the repo root with `claude --plugin-dir plugins/<plugin>`.
- Run the suites from the repo root, `uv run pytest`, `claude plugin test plugins/subagent-model` and `claude plugin test plugins/row-time`, then open a pull request to `main`.

## Adding or changing a rule

The Python rules' plugin is `plugins/rules/`, and each rule is a folder in its `scripts/` holding its script, its tests and its README. The rules that git enforces also share `scripts/git_hook.py`. A rule needs:

1. A folder `plugins/rules/scripts/<name>/`, named in snake_case after the rule, holding its script `rule.py`, with its logic in functions and its input (stdin, arguments or environment) read only under `if __name__ == "__main__":`, so its tests can import it. It must be executable, start with `#!/usr/bin/env python3`, and use only the standard library. For a `PreToolUse` rule, Claude Code passes it the tool call as JSON on stdin; to block the call, it writes the reason to stderr and exits 2, otherwise it exits 0. A rule that git enforces, such as Conventional Commits messages, instead registers the script as a git hook from a `SessionStart` hook, through `$CLAUDE_ENV_FILE`, by calling `register` from `scripts/git_hook.py` with the hook's name, its event, the command git is to run and the check it makes, and adds what it registers to `REGISTERED` in `scripts/test_git_hook.py`, whose tests check that the git rules register beside each other. Every git rule registers through that one function, never with export lines of its own, because the lines that register the rules must add to each other's and the user's `GIT_CONFIG_*` entries without replacing them, and must leave git working if a shell stops partway through them. Since git and Claude Code run the script by its path, which puts only the script's own folder on `sys.path`, the script puts the folder above it on `sys.path` before it imports `git_hook`, as the Conventional Commits rule does. Git then runs the command the rule registered, with that hook's arguments added after it, and to reject the git operation the script writes the reason to stderr and exits non-zero.
2. An entry in `plugins/rules/hooks/hooks.json`, under the event and matcher it applies to (such as `PreToolUse` on `Bash`, or `SessionStart`), that runs it as `"${CLAUDE_PLUGIN_ROOT}"/scripts/<name>/rule.py`.
3. Tests in `test_rule.py` beside the script, built by test-driven development, one realistic case per cycle. The tests import the script's functions, as `from .rule import …`, and call them directly; pytest's importlib import mode, set in `pyproject.toml`, keeps every rule's same-named files apart. The tests of the rules that git enforces take what they share, git kept apart from the user's own config and a Claude Code session to run it in, from `scripts/git_testing.py`, as `from ..git_testing import …`. The file starts with the docstring `"""Tests for "<the title of the rule's README>". Run from the repo root: uv run pytest"""`.
   - Red: write one test and run it. It must fail, and fail because the behaviour is missing, not with an error. A test that passes on its first run proves nothing until you have seen it fail against a deliberately broken version of the code.
   - Green: write the least code that makes it pass.
   - Refactor: with the test passing, improve the code and the tests without changing their behaviour; anything new starts its own cycle with a failing test. Re-run the tests for the code you changed after each change.
4. A `README.md` in the rule's folder, titled with the rule's name, saying what the rule blocks, what it allows, and why, and a row in the rules table of the plugin's README, `plugins/rules/README.md`, linking to it.

**A mod is NEVER a `.tsx` file and holds NO JSX.** Its code is `hooks/register.ts` and its tests are `tests/register.test.ts`, and whatever it draws it builds with plain `h(...)` calls.

A rule that needs a mod hook, such as one that checks each subagent as it starts, is instead a mod, and every mod is a plugin of its own, `plugins/<name>/`, named in kebab-case, because a plugin has one hooks module. It holds `.claude-plugin/plugin.json`; `hooks/hooks.json`, which names the module under `modules` by a path relative to that file, `./register.ts`; the module, `hooks/register.ts`, exporting `register` typed as `Register` from `'claude-code'`; its tests, `tests/register.test.ts`; a `README.md` saying what it does and why, then its Requirements and Install sections; and a `tsconfig.json` holding only `{"extends": "./.claude-plugin/types/tsconfig.json"}`, the file Claude Code itself adds to a mod that has none. It gets an entry in `.claude-plugin/marketplace.json` and a row in the plugins table of the repo's README, `README.md`, linking to its README. Its tests are built by the same cycle and run with `claude plugin test plugins/<name>`: each test raises events through the plugin with the kit's `$`, and the test's own `on` hooks stand for the engine beneath it. To type-check it, which needs TypeScript 5.5 or newer (`tsc`) installed, start an interactive session from the repo root with `claude --plugin-dir plugins/<name>` once, which lays Claude Code's types in `plugins/<name>/.claude-plugin/types/`, a folder that ignores itself in git, then run `tsc -p plugins/<name>`. Run `claude plugin validate plugins/<name>` after changing it.

A plugin that sets a Claude Code setting to run a script, such as `agent-row`'s `subagentStatusLine`, is also a plugin of its own, `plugins/<name>/`, named in kebab-case. It holds `.claude-plugin/plugin.json`, a `settings.json` that runs the script as `"${CLAUDE_PLUGIN_ROOT}"/scripts/<name>/<script>.py`, and a `README.md` saying what it does and why, then its Limits, Requirements and Install sections. The script and its tests, in `scripts/<name>/` named in snake_case, follow points 1 and 3 above, with the script's own name in place of `rule` and the plugin's README giving the tests' title, but nothing there about hooks applies. It gets an entry in `.claude-plugin/marketplace.json`, a row in the plugins table of the repo's README, and its folder in `testpaths` in `pyproject.toml`.

Name things so the code explains itself, and comment only on why, where the code cannot show it.
